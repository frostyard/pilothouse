# Change risk tiers

Classify every pull request before review by choosing the highest tier that
matches any part of its final diff. Classification is based on potential impact,
not line count, author, or whether a change was generated by an agent. A small
permission or broker change can carry more risk than a large documentation
update.

| Tier | Typical Pilothouse changes | Required handling |
|---|---|---|
| **Tier 1 — Low** | Documentation, comments, non-executable fixtures, or metadata that cannot affect application, build, package, configuration, workflow, or release behavior | Normal review and relevant repository checks |
| **Tier 2 — Moderate** | Routine UI or implementation changes and focused tests that stay outside privileged, security-sensitive, packaging, persistence, and operational boundaries | Required CI, regression coverage for changed behavior, and normal code review |
| **Tier 3 — High** | Capability detection or gating, dependencies, configuration schemas, ordinary workflow/build changes, broad validation changes, concurrency, durable state, external command integration, or non-privileged filesystem/network behavior | Tier 2 controls plus targeted failure-path validation, review by someone familiar with the affected area, and deployment or rollback notes when applicable |
| **Tier 4 — Critical** | Authentication, sessions, CSRF/origin enforcement, broker protocol or registration, PAM/systemd/package scriptlets, root or destructive host operations, authorized filesystem roots, release publication/signing, secrets or token permissions, execution derived from untrusted input, or automation that can approve or merge | Tier 3 controls plus explicit maintainer security review, threat or abuse-case analysis, a rollback plan, and confirmation that permissions and privileged surfaces remain least-privilege |

## Classification rules

- Choose the highest applicable tier; do not average different parts of a
  change.
- Treat a safeguard, test harness, or policy gate at the same tier as the
  behavior it protects.
- Raise the tier while impact is uncertain and lower it only after the
  uncertainty is resolved with evidence.
- Update the classification whenever the pull request scope changes.
- Never lower a tier to bypass required review, validation, or maintainer
  involvement.
- Classification adds handling requirements; it never replaces `make ci`,
  `make docker-ci`, specialized packaging/image gates, or repository
  invariants.

## Pull request evidence

Record the selected tier and a concise rationale in the pull request template.
For Tier 3 and Tier 4 changes, list the targeted failure-path checks and any
applicable deployment or rollback considerations. Tier 4 descriptions must also
identify the affected trust boundary and explain why privileges, accepted
inputs, and mutation scope are no broader than necessary.

Reviewers must compare the classification with the final diff before approval.
If any changed path or behavior belongs to a higher tier, request an updated
classification and its additional evidence before approving.
